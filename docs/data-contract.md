# Profile Data Contract

This document is the agreement used by both parts of the profile feature.
It was written before the topic and project code, so both branches build
against the same tables, status values and JSON shapes. Any change here
must be reviewed by both owners before either branch is merged.

## Ownership

| Area | Owner |
|---|---|
| Topic catalogue, student learning records, topic API, pandas topic processing, NumPy skill matrix | Bahodirjon |
| Project records and topic links, project API, pandas project summaries, NumPy counts from the matrix | Hasan |
| Generated skill labels, profile page, integration, cross-feature tests | Together |

## Database relationships

```
topic_catalogue (in code, not a table)
      │ topic_key
      ▼
students ──1:N──> student_topics <──N:M──> projects ──N:1──> students
                       │                      │
                       └──── project_topics ───┘
```

- `students` is unchanged: `id`, `name`, `topic`, `status`, `score`.
- `student_topics` has `id`, `student_id`, `topic_key`, `status`.
  `UNIQUE(student_id, topic_key)` prevents duplicate learning records.
- `projects` has `id`, `student_id`, `title`, `description`,
  `contribution`, `repository_link`, `status`.
- `project_topics` links `project_id` to `topic_id`. A link is valid only
  when the topic belongs to the same student as the project.
- Foreign keys are ON; deleting a student removes their topics, projects
  and project links. Deleting a topic removes its project links.
- The catalogue is predefined in `backend/config/business_rules.py` and
  exposed read-only through the API. A topic name can only be chosen from
  it, so every completed topic has exactly one mapped skill.

## Status values

| Record | Allowed values |
|---|---|
| Student topic | `Learning`, `Completed` |
| Project | `In progress`, `Completed` |

Statuses are deliberately different from the existing student statuses
(`Active`, `Paused`, `Completed`) and must not be mixed with them.

## API response formats

All responses are JSON. IDs are integers generated by SQLite. Validation
errors use FastAPI's normal 422 body; missing records use 404 with a text
`detail`, and a duplicate topic uses 409.

### Catalogue item and student topic

```json
{ "key": "git-branches-prs", "name": "Git branches and pull requests", "skill": "Git collaboration" }
```

```json
{
  "id": 3,
  "student_id": 1,
  "topic_key": "git-branches-prs",
  "topic_name": "Git branches and pull requests",
  "skill": "Git collaboration",
  "status": "Completed"
}
```

`topic_name` and `skill` are copied from the catalogue at response time,
so renaming a catalogue entry updates every response without a migration.

### Project

```json
{
  "id": 7,
  "student_id": 1,
  "title": "Student portfolio",
  "description": "A shared portfolio site for the academy cohort.",
  "contribution": "I implemented the Git branching workflow and PR review checklist.",
  "repository_link": "https://github.com/example/portfolio",
  "status": "Completed",
  "topic_ids": [3, 4]
}
```

`topic_ids` are IDs of that student's own `student_topics` records. Two
students may use the same title and description, but each record has its
own `contribution`.

### Generated skill

```json
{
  "name": "Git collaboration",
  "label": "Applied in a project",
  "topics": [
    { "id": 3, "name": "Git branches and pull requests", "status": "Completed" }
  ],
  "projects": [
    {
      "id": 7,
      "title": "Student portfolio",
      "contribution": "I implemented the Git branching workflow and PR review checklist.",
      "repository_link": "https://github.com/example/portfolio"
    }
  ]
}
```

Rules used to calculate it from the saved records:

1. Only `Completed` topics generate a skill. A `Learning` topic generates
   nothing.
2. All topics mapped to the same skill are merged into one entry.
3. The label is `Learned` unless a `Completed` project is linked to one of
   those supporting completed topics; then it is `Applied in a project`.
4. A project linked only to a `Learning` topic, or still `In progress`,
   never upgrades the label.
5. Changing a status or a topic link recalculates labels on the next read;
   labels are never stored in the database.

### Profile

```json
{
  "student": { "id": 1, "name": "Hasan", "topic": "Python", "status": "Active", "score": 80 },
  "topics": [ { "...": "StudentTopic" } ],
  "projects": [ { "...": "StudentProject" } ],
  "skills": [ { "...": "GeneratedSkill" } ],
  "summary": { "completed_topics": 1, "completed_projects": 1, "learned_skills": 1 }
}
```

### Skill matrix summary

```json
{
  "students": [{ "student_id": 1, "name": "Hasan" }],
  "skills": ["Git collaboration", "Python basics"],
  "matrix": [[1, 0]],
  "learned_skills_per_student": [{ "student_id": 1, "name": "Hasan", "count": 1 }],
  "students_per_skill": [{ "skill": "Git collaboration", "count": 1 }],
  "progress_per_student": [
    {
      "student_id": 1,
      "name": "Hasan",
      "completed_topics": 1,
      "completed_projects": 1,
      "learned_skills": 1
    }
  ]
}
```

`matrix[i][j]` is 1 when student `i` has at least one `Completed` topic
mapped to skill `j`. It is built with a NumPy integer array. `skills` is
the fixed catalogue order, so columns are stable even when counts are 0.

## Error cases agreed for tests

- Empty profile: all lists empty, all counts and matrix cells 0.
- Duplicate topic for the same student: 409, no second row.
- Unknown student, topic or project ID: 404.
- Unknown `topic_key`: 422.
- Project topic from another student: 422, no project saved.
- Several topics mapping to one skill: one skill with several `topics`.
- Status changes: profile and matrix recalculate from current records.
- Restart: records and calculated views come back from SQLite.

## Review checklist for both owners

1. Run `pytest` and `pycodestyle backend tests` on the merged branch.
2. Run the app and open the profile for a student with no records, one
   with only a completed topic, and one with a completed linked project.
3. Change each status in both directions and confirm the profile changes.
4. Add a test for the teammate's area on the integration branch.

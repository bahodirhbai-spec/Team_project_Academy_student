# 🪾 Git Branch

Branches let you work on different features or fixes without affecting the main codebase. Think of branches as parallel versions of your project where you can experiment safely.

**Why use branches?**

- Work on features without breaking the main code
- Multiple team members can work simultaneously
- Easy to test and review changes before merging
- Quick rollback if something goes wrong

!!! warning
    Don't be a that developer who always works directly on `main` and breaks everything:

## Basic Commands

### Create a New Branch

```bash
git branch feature/login
```

### Create and Switch to New Branch

```bash
git checkout -b feature/login
```

Or with newer Git versions:

```bash
git switch -c feature/login
```

### Switch Between Branches

```bash
git checkout main
# or
git switch main
```

### List All Branches

```bash
# Local branches
git branch

# All branches (including remote)
git branch -a
```

### Delete a Branch

```bash
# Delete local branch (safe - won't delete unmerged changes)
git branch -d feature/login

# Force delete local branch
git branch -D feature/login

# Delete remote branch
git push origin --delete feature/login
```

### Rename a Branch

```bash
# Rename current branch
git branch -m new-name

# Rename a specific branch
git branch -m old-name new-name
```

## Branch Naming Conventions

Good branch names help your team understand what each branch contains at a glance.

### Format

```text
<type>/<short-description>
```

### Branch Prefixes

| Prefix | Purpose | Example |
| ------ | ------- | ------- |
| `feat/` | New features | `feat/user-auth` |
| `fix/` | Bug fixes | `fix/login-crash` |
| `hotfix/` | Urgent production fixes | `hotfix/security-patch` |
| `release/` | Release preparation | `release/v1.2.0` |
| `docs/` | Documentation updates | `docs/api-guide` |
| `refactor/` | Code refactoring | `refactor/database-layer` |
| `test/` | Testing related | `test/payment-flow` |
| `chore/` | Maintenance tasks | `chore/update-deps` |
| etc. | Define based on project needs | |

!!! note "Automated tool prefixes"
    Automated tools create their own branch prefixes. For example:

    - `dependabot/` - Dependency updates (e.g., `dependabot/npm_and_yarn/lodash-4.17.21`)
    - `renovate/` - Renovate bot updates
    - `snyk-` - Snyk security fixes

### Jira Integration Format

For automatic integration with Jira, your Git branch names must include the Jira Issue Key to ensure the development panel accurately tracks your progress.

**Format:**

```text
<prefix>/<ISSUE-KEY>-<brief-description>
```

| Part | Description | Example |
| ---- | ----------- | ------- |
| Prefix | Categorizes the work | `feature/`, `bugfix/`, `hotfix/` |
| Issue Key | The unique Jira ticket ID | `PROJ-123`, `WEB-456` |
| Description | Short, kebab-case summary | `update-login-api` |

**Examples:**

```bash
feature/WEB-456-user-authentication
bugfix/PROJ-123-fix-payment-flow
hotfix/API-789-security-patch
```

!!! note
    The Issue Key must remain in the branch name for the Jira integration to work.

!!! tip
    When Jira auto-generates a branch name, you can edit it to add the type prefix (e.g., `feature/`, `bugfix/`) before creating the branch.

*Source: [Mastering Jira Git Workflows](https://www.linkedin.com/pulse/mastering-jira-git-workflows-optimal-project-antoine-fusilier-gr6ke/)*

### Naming Rules (MANDATORY)

**Do:**

- Use lowercase letters
- Use hyphens to separate words
- Keep names short but descriptive
- Include ticket number if applicable
- Use `/` to separate prefix from description
- `.` and `_` are acceptable (e.g., `feature/api_v2.0`)

**Don't:**

- Use spaces (use hyphens instead)
- Use special characters (except `-`, `_`, `.`, `/`)
- Make names too long
- Use vague names like `stuff` or `changes`

### Good Examples

```bash
feat/add-cart
fix/login-crash
hotfix/security-patch
feat/JIRA-123-profile
fix/johns-fix
```

### Bad Examples

```bash
new_feature           # Vague, no type prefix
Fix Login             # Spaces, uppercase
feature/add-new-user-authentication-flow-with-oauth  # Too long
john-branch           # No type 
test123               # Meaningless
```

## Branch Types

### Branch Requirements

| Team / Project Type | Required Branches | Recommended |
| ------------------- | ----------------- | ----------- |
| Solo developer | `main`, `dev` | - |
| 2+ developers | `main`, `dev`, `feature/*` | Any additional branches |
| Deploys to production (small projects without database) | `main`, `dev`, `feature/*` | `prod`, `hotfix/*` |
| Deploys to production (large projects or has database) | `main`, `dev`, `feature/*`, `prod` | `hotfix/*`, `test`, `staging` |

!!! note "When is `prod` branch required?"
    The `prod` branch is **MANDATORY** for large projects deployed to production environments (AWS, GCP, on-premise servers, etc.) or have a database. For smaller projects without a database, `prod` is just RECOMMENDED.

### Main Branch (`main`)

The production-ready branch. Code here should always be stable and deployable.

**Rules:**

- Never commit directly to `main` (REQUIRED)
- All changes come through Pull Requests
- Protected by branch protection rules
- Tagged with version numbers for releases

### Development Branch (`dev`)

The integration branch where features come together before release.

**Rules:**

- Contains the latest development changes
- Should be relatively stable
- Features are merged here first
- Use PRs for big teams; direct commits OK for small teams

### Feature Branches

Short-lived branches for developing new features.

**Rules:**

- Branch from: `dev` (or `main` in simpler workflows)
- Merge back to: `dev`
- Naming: `feature/description`
- Delete after merging (RECOMMENDED)

```bash
# Create feature branch
git checkout dev
git checkout -b feature/user-dashboard

# Work on feature...
# When done, create PR to dev
```

### Hotfix Branches

Emergency branches for critical production fixes.

**Rules:**

- Branch from: `main`
- Merge back to: `main` AND `dev`
- Naming: `hotfix/description`
- Should be fixed and merged quickly

```bash
# Create hotfix branch
git checkout main
git checkout -b hotfix/security-vulnerability

# Fix the issue...
# Merge to main AND dev
```

### Environment Branches

Long-lived branches that map to deployment environments. Code is promoted through environments to ensure quality before reaching production.

| Branch | Purpose | Deploys To |
| ------ | ------- | ---------- |
| `dev` | Development and early testing | Development environment |
| `test` | Automated testing (CI/CD) | Test environment/server [OPTIONAL] |
| `staging` | Pre-production QA, demos | Staging server |
| `prod` | Live application | Production server |

**Flow:**

```text
feature → dev → test (optional) → main → staging → prod
```

If project doesn't have deployment, just publish to storage/artifact/registry from `main`:

```text
feature → dev → test (optional) → main
```

**Rules:**

- `dev` - All feature branches merge here first for initial testing
- `test` - Automated tests run here (CI/CD pipelines)
- `main` - Stable code ready for staging
- `staging` - Manual QA, security testing, client demos
- `prod` - Only code that is ready for live **production** or already deployed, mirror of production

**Hotfix flow:**

```bash
# Create hotfix from prod
git checkout prod
git checkout -b hotfix/critical-fix

# After fix, merge to all environments
# prod → staging → main → test → dev
```

!!! warning
    Never merge to an environment branch unless you're ready to deploy to that environment.

*Source: [Git Flow vs Three-Branch Strategy](https://medium.com/@marcelokopmann/git-flow-vs-three-branch-strategy-dev-staging-prod-3ec023c51e8a)*

## Branching Strategies

### 1. GitFlow (RECOMMENDED)

A structured workflow with multiple long-lived branches. Best for projects with scheduled releases.

![Gitflow Workflow](../../assets/images/gitflow-workflow.jpg)

**Branches:**

- `main` - Production code (for us it's `prod`)
- `hotfix/*` - Production fixes
- `release/*` - Release preparation (for us it's `main` or `staging`)
- `dev` - Development integration
- `feature/*` - New features

**When to use:**

- Scheduled release cycles
- Multiple versions in production
- Larger teams needing structure

**When NOT to use:**

- Continuous deployment environments
- Small teams or solo projects

### 2. Trunk-Based Development (NOT RECOMMENDED)

Everyone commits to a single main branch with short-lived feature branches.

![Trunk Based Development](../../assets/images/git-branch-trunk.png)

*Source: [Aviator](https://www.aviator.co/blog/trunk-based-development-in-microservices/)*

**How it works:**

- Single `main` branch (the "trunk")
- Very short-lived feature branches (hours to days)
- Frequent merges to main
- Feature flags for incomplete work

**When to use:**

- Continuous integration/deployment
- Small to medium teams
- Fast-moving projects

**Benefits:**

- Fewer merge conflicts
- Faster feedback
- Simpler workflow

## Best Practices

### 1. Keep Branches Short-Lived (RECOMMENDED)

Long-running branches lead to merge conflicts. Try to merge within a few days.

!!! note
    Private/personal branches can be long-lived if needed for ongoing experiments or work-in-progress.

### 2. Stay Updated with Base Branch (RECOMMENDED)

Regularly pull changes from the branch you'll merge into. Also keep `dev` updated after hotfixes are merged to `main`.

**Complete workflow (after hotfix merged to main):**

```bash
# 1. Update local main
git checkout main
git pull

# 2. Update dev with main changes
git checkout dev
git pull
git merge main
git push

# 3. Update your feature branch
git checkout feat/my-feature
git merge dev
```

### 3. One Purpose Per Branch (REQUIRED)

Each branch should have a single purpose. Don't mix features and bug fixes.

### 4. Delete Merged Branches (RECOMMENDED)

Clean up after yourself:

```bash
# Delete local branch
git branch -d feature/completed-feature

# Delete remote branch
git push origin --delete feature/completed-feature
```

!!! tip
    You can use `git fetch --all --prune` to remove all local tracking branches that no longer exist on the remote.

## Common Issues

### Branch Already Exists

```text
fatal: A branch named 'feature/login' already exists.
```

**Solution:** Choose a different name or delete the existing branch if it's no longer needed.

### Cannot Delete Branch (Unmerged Changes)

```text
error: The branch 'feature/login' is not fully merged.
```

**Solution:** Either merge the branch first or use `-D` to force delete (you'll lose changes).

### Detached HEAD State

```text
You are in 'detached HEAD' state.
```

**Cause:** You checked out a commit instead of a branch.

**Solution:**

```bash
# Create a new branch from current state
git checkout -b my-new-branch

# Or go back to a branch
git checkout main
```

### Merge Conflicts

**Cause:** Same lines were changed in both branches.

**Solution:**

1. Open conflicted files
2. Look for conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`)
3. Resolve conflicts manually
4. Stage and commit the resolution
